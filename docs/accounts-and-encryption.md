# Company accounts and protected data

This release introduces separate company databases, owner/agent/reviewer memberships, provider sign-in, onboarding, cookie sessions and email-bound invitations. It replaces shared Basic authentication for public deployments. OAuth and email adapters require the configuration and live acceptance tests below; mocked identity tests are not a live-provider certification.

## Signup and sign-in

1. The visitor opens `/signin` and chooses Google or Apple. Disabled buttons mean credentials are absent.
2. A ten-minute, single-use server-side flow binds the authorization response to the browser with a random state, nonce and HttpOnly cookie. Google also uses PKCE. Tokens are exchanged on the server and verified with the provider's public keys, issuer, audience, expiry and nonce. Unverified email claims are rejected. Identity is keyed by provider plus subject; accounts are not automatically linked by email.
3. A fresh opaque session is created; only its SHA-256 hash is stored. Cookies are HttpOnly, SameSite=Lax, Secure on HTTPS, scoped to the host and expire after twelve hours. Apple's cross-site form callback uses a short-lived Secure SameSite=None flow cookie, with state/browser binding. Logout deletes the session; membership is rechecked on each protected request.
4. The user accepts the versioned terms and acknowledges the account privacy notice. These acknowledgements are recorded separately from optional AI processing; there is no marketing subscription or blanket consent.
5. The user names their company. The server provisions a separate PostgreSQL database, policies and default privacy settings. External AI and integrations are off. No customer records are copied from the legacy demonstration database. Fictional action resources remain clearly labelled as demonstrations.
6. The creator becomes owner. Current public signup is limited to fifty workspaces by `MAX_WORKSPACES`; raise only after measuring database/pool capacity. Each user can create one owned company and join additional companies by invitation. This is a single-instance pilot architecture, not a claim of unlimited SaaS scale.

## Invite a teammate

An owner opens **Account & team**, enters an email address and chooses agent or reviewer. The server stores a keyed hash of the destination, workspace, role, inviter and a hash of a random invitation token. Links expire after 24 hours and are consumed atomically once. The recipient must authenticate with the same provider-verified email. Existing members keep their existing role; accepting another invitation cannot promote them. Apple Hide My Email recipients must use the actual verified relay address displayed in their account, or sign in with the invited address through another provider.

Set `INVITE_EMAIL_API_KEY` and `INVITE_EMAIL_FROM` for Resend delivery from a verified sending domain. No provider key means no email is sent: the owner gets a private link to share with the intended teammate. Delivery failure is reported honestly and does not silently retry. Do not publish invitation links. Owners can remove staff access; the next request is denied even if their session cookie remains. Owners cannot remove the owner account through that action.

Agents can work with requests. Reviewers can additionally execute/reconcile eligible actions. Owners manage company/privacy/integration settings, team invitations and API credentials. UI visibility does not authorize actions; the API checks the current membership and role. API keys are company-scoped, stored only as hashes and shown once when generated. Rotating a pair revokes both old keys. Only the authenticated Agent API namespace is exposed through the Astro HTTPS gateway; operator APIs remain private.

## Company isolation

The authentication catalogue stores identity, sessions and memberships. Each company's operational data, policies, workflows, credentials and action state live in its own database. A server-resolved session or scoped API credential selects that database; the browser cannot choose a database name. Async request context follows provider calls, worker work and Slack event handlers. Provider secrets are company-scoped and encrypted; new companies do not inherit environment keys, Stripe customers, service connectors or Slack channels from the legacy demo. Global OAuth and email credentials belong to Resolve's account service.

The database server role currently needs CREATE DATABASE and migration privileges. Protect it as a high-value server credential. This architecture isolates application queries, not a compromised database administrator or server process. Run one app replica: the queue recovery and provisioning design is not a multi-instance lease protocol. Separate databases use small pools, but a larger public service needs provisioning quotas, better pool lifecycle management, durable queue leases and operational monitoring.

## Encryption and minimum collection

AES-256-GCM with fresh 96-bit nonces encrypts customer names, titles, messages, summaries, assignees, tags and customer references; company/privacy profiles; model run content; workflow payloads, private connector plan references and fictional service state; provider credentials; account email and transient OAuth flow secrets. HKDF derives different storage keys per company from `DATA_ENCRYPTION_KEY`; authentication-catalogue records use a distinct derivation. Field names are authenticated as associated data. Tampered ciphertext or a wrong company/key fails closed. There is no plaintext fallback. The migration encrypts existing active rows in batches inside the migration transaction.

Lookup keys and operational metadata remain queryable: IDs, payment references with uniqueness constraints, status, amount, timestamps, membership/role, source identifiers and workflow retention metadata. Hashes are not anonymous data. **The complete PostgreSQL data directory, its write-ahead logs and backups must also reside on encrypted storage** to cover this metadata and remnants from before the migration. The deployment Compose file requires an existing `POSTGRES_DATA_PATH`; it does not create or attest an encrypted filesystem. On DigitalOcean use an encrypted Volume, verify its mount and use its directory. Encryption at rest does not protect a stolen running-server credential.

Use HTTPS for browsers. Keep the database/API private. For remote PostgreSQL set `DATABASE_SSL=true` and supply `DATABASE_CA_CERT` when needed; certificate verification stays enabled. Local Compose database traffic is on the private host network and is not TLS-encrypted; it must not be exposed publicly. Back up the encryption master key separately and securely. Do not rotate it by generating a replacement: existing ciphertext and keyed identity hashes require the original key until a controlled re-encryption/key-migration process exists.

Collected account fields: provider/subject keyed hash, verified encrypted email (needed for invitations), company membership/role, versioned terms/privacy acknowledgement, account creation time for abandoned-signup retention, and hashed session/expiry. No profile photo, contacts, inbox access, provider refresh-token persistence, advertising trackers or optional marketing data is requested. OAuth access/refresh tokens are discarded after verification. Uncompleted accounts without memberships are removed after 30 days when sign-in maintenance runs; expired flows/sessions/invites are also cleaned up. Existing conversation retention remains active in each company. Account deletion, provider account-change notifications and fully orchestrated rights fulfilment are still separate reviewed work.

This is server-readable encrypted storage, not end-to-end encryption. Authorized processing decrypts content in server memory; explicitly enabled AI may receive minimized text under company policy. Filtering cannot guarantee anonymization. Deployment, provider agreements, retention operations, incident procedures and reviewed legal documents remain necessary; this feature does not certify GDPR compliance.

## Provider setup and live acceptance

- Google: create a Web application OAuth client. Set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`; register `https://YOUR_DOMAIN/auth/callback/google` exactly. Only `openid email` scopes are requested.
- Apple: configure a Services ID and web domain/return URL, and generate a valid signed client-secret JWT using your Apple Developer key. Set `APPLE_CLIENT_ID` and `APPLE_CLIENT_SECRET`; register `https://YOUR_DOMAIN/auth/callback/apple`. Apple requires a real HTTPS domain. Maintain client-secret rotation/expiry; the private signing key is not collected by this app. Only email is requested, not name.
- Resend: configure a verified sender and the two invitation variables. A working link without the delivery key is not evidence that an email was sent.
- Set `ALLOW_BASIC_AUTH=false` for public deployments. Setting it true enables the isolated legacy demo boundary with the shared workspace password; do not enable that bypass for a public release.
- Confirm both providers with real accounts, denied consent, wrong/expired state, logout, invitation to an existing/new account, wrong email, expiry, reuse and staff revocation. Check HTTPS cookie flags and proxy-origin behavior on the actual domain. Complete deployment health checks and backup/restore before real customer use.
